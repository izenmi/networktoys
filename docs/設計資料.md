# NetworkToys 設計資料

C# + WPF + .NET 10 / 単一 exe / 依存パッケージ 4 つ

> 2026-08-17 版　／　リポジトリ: izenmi/networktoys（MIT）
> この資料は `docs/設計資料.md` から `tools/docs/build_docx.py` で焼いています。
> 実装上の細かい罠は `CLAUDE.md`、当初の設計経緯は `DESIGN.md` にあります。

## 1. 何を作っているか

ネットワーク作業の前後を測り、切り分け、証跡に残すための Windows ネイティブアプリ。**宛先ごとに独立した周期で並列に ping を打つ**ことが第一の目的で、そこに現場で必要になる道具（TCP 疎通・DNS・経路・スキャン・無線・syslog 受信・機器へのログイン・設定差分・各種コントローラの照会）を同じアプリへ集めている。

| 項目 | 決定 | 理由 |
|---|---|---|
| 技術 | C# + WPF + .NET 10 (LTS) | ICMP / TCP / DNS / Wi-Fi がすべて標準 API と P/Invoke で素直に叩ける。単一プロセスで追加ランタイムが要らない |
| 配布 | self-contained 単一 exe ＋ ランタイム別途版 | 起動 0.6 秒・メモリ 90MB 台を実測で確認済み |
| ビルド | GitHub Actions `windows-latest` | 開発環境が Linux で dotnet SDK を持たないため |
| 権限 | `asInvoker` 固定 | 全機能を非管理者で動かす方針（例外は後述の 2 つだけ） |

## 2. 最大の制約 — ローカルで一度も実行できない

開発コンテナは Linux で、dotnet SDK が無く、Windows 側ドライブも見えない。**exe をコンパイルすることも実行することもできない。GitHub Actions が唯一のコンパイラであり、唯一の実行環境**という前提で設計が組んである。

対策は 3 つで、これがこのリポジトリの構造そのものになっている。

### ① テストできない部分を、テストできる純関数の薄いラッパーに追い込む

ネットワークにも WPF にも触らないコード（IP 範囲パース、統計、MOS 算出、OUI 解決、レポート生成、機器出力の解釈、API 応答の解釈）はすべて `NetworkToys.Core` (net10.0) に置き、xUnit で検証する。

たとえば traceroute なら「Ping を投げる部分」と「ホップ列を解析・整形する部分」を分け、後者を固定データでテストする。Cisco 機器との対話は状態機械を `Stream` の上に書いて Core に置き、**メモリ上の偽 Cisco 機器と会話させて完走できる**ようにしてある。同じ手を、偽の STUN サーバ・偽の APIC・偽の WLC・偽の Catalyst Center・自前 FTP サーバとの往復にも使っている。

### ② `--selftest`

`NetworkToys.exe --selftest` で自己診断し、終了コードを返す。**XAML の誤り（リソースキーの打ち間違いなど）はコンパイルを通り抜けて実行時に落ちる**ため、MainWindow を実際に生成・表示するこの検査が実質唯一の防波堤になっている。

いま見ているものの例:

- 全タブ・全サブタブを実体化して表示できるか
- どのタブにも 1 行の説明と ⓘ があり、体裁の決まり（1 行目はタブ名・箇条書き・全角 68 字）を守っているか
- 一覧の見出しと行の左右の余白が噛み合っているか（16 表を突き合わせ）
- 明暗パレットに同じ色キーが揃っているか、文字と地のコントラストが WCAG 4.5:1 以上か
- 右クリックからアドレスを取り出せる行の型が漏れていないか
- 秘密情報の入れ物（パスワード・API キー）がプロパティとして存在しないか
- タブを開いただけで外部 API を叩き始めないか

### ③ 1 フェーズ = 1 まとまり = CI グリーン

大きな差分を積むと失敗の切り分けが不可能になる。フェーズごとに必ず緑にしてから次へ進む。

## 3. 全体の構成

```
networktoys/
├── src/NetworkToys.Core/    net10.0     Windows 非依存・テスト対象。ここを厚くする
├── src/NetworkToys.App/     net10.0-windows  WPF 本体。Core を参照する（逆参照は禁止）
├── tests/                   xUnit       CI で必ず実行
└── tools/                   手動スクリプト（OUI テーブル生成・アイコン・この資料）
```

| 層 | 置くもの | 規模 |
|---|---|---|
| `NetworkToys.Core` | 解釈・計算・整形。HTTP にもソケットにも WPF にも触らない | 約 16,600 行 |
| `NetworkToys.App` | 画面（XAML）・ViewModel・実際に通信する Services・P/Invoke | 約 29,300 行 ＋ XAML 約 10,000 行 |
| `tests` | Core のユニットテスト（`[Fact]` / `[Theory]` 約 850 件・68 ファイル） | 約 11,800 行 |

**依存の向きは App → Core の一方通行。**逆参照を禁じているのは、Core がテスト可能であり続けるため。

### 依存パッケージ

| パッケージ | 用途 | 選んだ理由 |
|---|---|---|
| `ManagedNativeWifi` 3.0.2 | Native Wifi API のラッパ | 依存パッケージを持たない。ほかの選択肢は自前 P/Invoke になる |
| `DnsClient` 1.8.0 | 任意レコードの DNS 照会 | **問い合わせ先の DNS サーバを指定できる**（標準の `System.Net.Dns` は A/AAAA/PTR しか引けず、サーバも選べない） |
| `FxSsh` 1.4.0 | SFTP サーバの SSH 層 | SSH の自前実装は非現実的 |
| `SSH.NET` 2026.0.0 | SSH / SFTP のクライアント | 同上 |

**入れないもの**: グラフ描画・JSON・HTTP・SQLite・MVVM・Excel のライブラリ。`ObservableObject` と `RelayCommand` は合わせて 40 行で足り、xlsx は zip に XML を 5 枚入れれば作れる。**ローカルでビルドを確認できない状況では、バージョン依存を持ち込む方がリスクが大きい。**

同梱物のライセンス表示は `THIRD-PARTY-NOTICES.txt` に置き、**csproj の `PackageReference` と突き合わせる xUnit** で書き忘れを防いでいる（MIT / Apache-2.0 / OFL 1.1 はいずれも再配布時の添付が条件）。

## 4. 中核の設計判断

### 並列 ping — 「ラウンド同期」にしない

**全宛先を 1 ラウンドずつ `Task.WhenAll` で回すのではなく、宛先ごとに独立した周期ループを持たせる。**ラウンド同期方式では、タイムアウトする 1 宛先が他の全宛先を待たせてしまい、EXPing と同じ待たされ感が残る。

| 決まり | 理由 |
|---|---|
| `Ping` インスタンスは宛先ごとに 1 つ | 同時に 1 リクエストしか扱えない（進行中に再送すると例外）。1 宛先で同時に複数投げる traceroute ではプールする |
| RTT は自前の `Stopwatch.GetTimestamp()` で測る | `PingReply.RoundtripTime` は失敗時に 0 を返し信用できない |
| `Task.Run` で同期版を包まない | 非同期 API は I/O 完了ポートを使うので数百同時でもスレッドを消費しないが、包むとスレッドプールが枯渇する |
| 履歴は固定長リングバッファ（既定 300） | サンプルは構造体で持ち GC 圧を避ける |
| ホスト名は起動時に一度だけ解決 | 毎回 DNS を引かない |
| TCP は `LingerOption(true, 0)` の RST クローズ | 行儀よく閉じると TIME_WAIT が 4 分残り、一時ポートを食い潰す。測定用の接続はデータを流さないので RST で切ってよい |

### UI への反映 — ここを外すと重くなる

- 測定スレッドから `ObservableCollection` を直接触らない。結果は `Channel` に積み、**UI 側で 10Hz にまとめて反映**する（500 宛先 × 1Hz = 500 通知/秒で UI が溶ける）
- 構造の変化は宛先の増減時のみ。測定結果は既存の行 ViewModel のプロパティ更新として流す
- 一覧は仮想化必須（`VirtualizationMode=Recycling`・行高固定）。**仮想化の指定は ItemsControl 側の添付プロパティに書く**（パネル要素に書いても無言で無視される）
- スパークラインは `Polyline` ではなく `DrawingVisual` へ直接描画

### 画面の作り

- **タブの入れ子は 2 段まで。**3 段にすると道具を探せなくなる
- 単独のタブを左、まとめたタブ（「その他」1 枚）を右に置く。中身 19 枚の分類は各 `TabItem` の `Tag`（調べる / 受ける / NW機器）で持ち、見出しの件数は自己診断が実際の本数と突き合わせる
- **どのタブにも先頭に 1 行の説明と ⓘ を置く。**タブ名だけでは何の画面か伝わらない。詳しい説明は `Help/TabHelp.cs` に置く（XAML の属性値だと改行が書けず、レビューも成り立たない）
- 列幅は `ViewModels/TableColumns.cs` の宣言 1 か所で持ち、見出しと行が同じキーで引く。**ドラッグは「掴んでからの総移動量」で決める**（1 回ぶんの差分を足し込むと、幅を変えるとつまみ自体が動くため伸び縮みが鈍る）
- 見出しと行の左右の余白は 1 つの規約に揃える（見出し `4,0,18,3` ／ 行 `Padding="4,0"` ／ 縦スクロールバー常時確保）。**16 表のうち 10 表が一度これでずれた**ので、自己診断が全タブを回って突き合わせている
- 状態は**色だけで表さない**。記号と文字を必ず併記し、色は補助にとどめる

### 外部の機器・API を扱うときの共通方針

Cisco ACI (APIC) / Catalyst 9800 (RESTCONF) / Catalyst Center / Meraki ダッシュボードの 4 系統を扱っているが、方針は同じ。

| 方針 | 中身 |
|---|---|
| **読み取り専用** | POST するのはログインとログアウトだけ。設定を書く機能は作らない。本番設備を握るので、書ける口があること自体が事故の入口になる |
| **型付きの POCO を作らない** | 応答の項目は版で増減し、型を決め打ちすると 1 台の想定外で一覧が丸ごと落ちる。`JsonDocument` で必要な項目だけ拾い、**無ければ空文字。例外にしない** |
| **項目名の候補を 1 か所に並べる** | リーフ名やパスは版で動く。実機で外れたら 1 行足せば直る形にしておく |
| **秘密情報を保存しない・入れ物も作らない** | 設定に持つのは接続先・ユーザー名・受け入れた証明書の指紋だけ |
| **自己診断から実機を叩かない** | タブを開いただけでは通信しない作りにする（CI の Windows ランナーは外に出られるため）。検査は偽サーバとの往復で行う |
| **「応答を表示」を外さない** | 項目名の思い違いは実機でしか分からない。これが無いと「表が空」から先へ進めない |
| **打ち切ったことは必ず画面に出す** | ページングは 20 ページで打ち切る。黙って切ると「その機器は無い」と誤読される |

### 秘密情報の扱い

- パスワードは保存しない。`AppSettingsDocument` にも昇格時の引き継ぎファイルにも**入れ物を作らない**（自己診断が名前で検査している）
- Meraki の API キーは毎回入力。入力欄は `PasswordBox`（`TextBox` にすると画面の PNG 保存に焼き込まれる）
- エラーメッセージは応答本文を読まず、ステータスコードから組み立てる（本文に鍵が載る可能性を持ち込まない）
- 機器のパスワードを 2 回聞かれたら認証失敗として即中断する（TACACS+ / AD でアカウントを固めない）

## 5. 品質をどう担保しているか

| 手段 | 何を守れるか |
|---|---|
| xUnit（Core、約 850 件） | 解釈・計算・整形のすべて。往復テストが書けるものは書く（FTP の一覧・xlsx・差分） |
| `--selftest` | XAML の実体化、画面の規約、秘密情報の不在、配色のコントラスト、P/Invoke の合成バッファ検査 |
| CI（`windows-latest`） | test → publish 2 構成 → exe 起動スモーク → `--selftest` → 成果物。タグを打つと Release まで |
| 実機確認 | 見た目の印象、数百宛先での描画、Wi-Fi API の実際の応答、外部 API の実応答 |

**CI で分かるのはビルド成否・ユニットテスト・起動可否まで。**見た目と実機の挙動はユーザーに確認してもらうしかないため、フェーズ完了時にスクリーンショットを依頼する運用にしている。

### 実際にこの網が捕まえたもの（例）

- 収集タブで `--More--` を検出前に消していた／すでに特権の機器へ enable を二重に投げていた
- Meraki の 4 一覧が既定の `ListBoxItem` で描かれ、行だけ余白がずれていた
- スクロールバーが出た瞬間に行だけ 14px 狭くなり、可変幅列より右が全部ずれていた（16 表中 10 表）
- `InvariantGlobalization=true` が publish は通るのに、最初の TextBlock を測った瞬間に落ちていた

## 6. 配布

### Phase 0 の実測（GitHub Actions の windows-latest 上）

| 構成 | GUI 起動 | メモリ | 配布サイズ | 採否 |
|---|---|---|---|---|
| 単一 exe + R2R | 663 ms | 93.5 MB | 124.8 MB | **採用（既定）** |
| 単一 exe のみ | 639 ms | 93.3 MB | 124.7 MB | R2R と差がないので R2R 有効のまま |
| R2R のみ（フォルダ配布） | 641 ms | 91.1 MB | 131.2 MB | 単一 exe の利点がない |
| 単一 exe + 圧縮 | 720 ms | 182.7 MB | 58.6 MB | 不採用（メモリ 2 倍・初回起動 5 秒） |
| ランタイム別途 | 683 ms | 91.2 MB | 0.2 MB | **併せて配布**（サイズ重視の選択肢） |

**WPF はトリミングできない**（`PublishTrimmed` も `PublishAot` も不可）ため、サイズは削れない前提で「軽量」を起動時間とメモリで満たす方針にしている。`InvariantGlobalization=true` は WPF では使えない（ICU が同梱されず、フォントキャッシュの型初期化に失敗する）。

### 署名

**未署名で配っている。**そのため Chrome と SmartScreen が警告を出す。どちらも「危険」ではなく「署名が無く、まだ広まっていない」という判定で、評判はバイナリのハッシュ単位に貯まるため**リリースのたびにゼロに戻る**。

補える範囲は 3 つ: `SHA256SUMS.txt` の添付（実装済み）、ビルドを CI だけで行いログを公開したままにする（実装済み）、誤検知として報告する（README に導線）。恒久的に消すにはコード署名証明書が要る。2023 年 6 月以降、秘密鍵はハードウェア保管が必須になったため、CI から署名するならクラウド署名サービス（Azure Trusted Signing / SignPath Foundation）を選ぶことになる。

**難読化や圧縮で検知を避けにいかないこと。**効果が薄いうえ、高エントロピーなバイナリはかえってヒューリスティックに引っかかる。

## 7. 保存するもの

設定は **exe と同じフォルダ**に置く（持ち出して使うための作り）。書き込めない場所に置かれたときだけ `%APPDATA%\NetworkToys\` へ逃がす。判定は属性ではなく**実際に 1 ファイル書いて消して**行う。

| ファイル | 中身 |
|---|---|
| `settings.json` | すべての設定（宛先リスト・測定の既定値・配色・列幅・接続先・受け入れた指紋） |
| `logs\` | 測定ログ（1 結果 1 行のタブ区切り）とスクリーンショット。30 日で整理 |
| `sessions\` `collect\` `ftp\` `tftp\` `sftp\` | 作業記録・収集した出力・受け取ったファイル |

**設定ファイルを増やさない。**新しい設定は `AppSettingsDocument` にプロパティを足す（旧 4 ファイルは初回起動時に取り込んで片付けた）。

## 8. やらないと決めたこと

一度作って消したもの、検討して見送ったものを、再提案しないために残しておく。

| もの | 顛末 |
|---|---|
| 一望表示（1 行に複数エントリを並べるタイル表示） | 自作の仮想化パネルまで作ったが、ユーザー指示で削除 |
| プロファイル（接続環境による宛先の自動切替） | 実装後に削除。宛先リストをテキストで手元管理する方が早い、が使ってみた結論 |
| 無線サーベイ（フロア図＋ヒートマップ） | 実装後に削除 |
| 音の通知・見張りモード | 削除済み |
| 記録タブ | 畳んで、書き出しはファイルメニューへ |
| `▲ 遅延` の状態表示 | 廃止 |
| SQLite / MVVM / Excel / グラフのライブラリ | 標準機能と自前実装で足りるため入れない |
| コード署名 | 費用と運用の判断待ち（選択肢は本資料 6 章のとおり） |

## 9. これから触る人へ

1. **`CLAUDE.md` を先に読む。**実装上の罠が調査済みで並んでいる（踏む前に読むためのもの）
2. **ロジックは Core へ押し出す。**「テストできない部分を、テストできる純関数の薄いラッパーに追い込む」が唯一の安全網
3. **新しい画面やリソースを足したら `--selftest` に検査を足す。**XAML の誤りはコンパイルを通り抜ける
4. **1 フェーズごとに CI を緑にしてから次へ進む**
